# ECC owns the private Studio runtime

ECC publishes one executable that serves both users and Studio: the normal `ecc` CLI also provides the private `ecc rpc serve --stdio --persistent-db` entrypoint. The `rpc` command is hidden from ordinary CLI help and user documentation but remains covered by internal integration documentation and tests. ECOS Studio does not build, stage, validate or sandbox a second `ecos-ecc-runtime-adapter` or `ecc-runtime` binary; Electron launches the pinned packaged `ecc` executable with Runtime arguments, and source development uses the existing ECC wrapper.

ECC CLI and ECC Runtime share one sibling Workspace Ownership Lock for every Workspace execution or durable mutation, including configuration, rerun preparation, recovery and saved layout edits. Process-local Session locks remain internal coordination and never replace this cross-process exclusion. Pure queries take no exclusive Workspace lock and read only atomically replaced committed files.

Any ECC API that mutates both a Project Manifest and a Workspace acquires locks in the single order `Project Manifest Lock -> Workspace Ownership Lock`; Workspace-only operations acquire only the latter, and Manifest-only operations acquire only the former. Project API callers enter the Manifest Lock before invoking a lock-aware Workspace transaction, preventing reverse-order deadlocks during create, structural update, overwrite recovery or registration rollback.

ECC Runtime attempts this lock without waiting. A lock held outside its Runtime Session returns the stable retryable error `workspace_busy` without guessing an owner; a known Active Operation in the same Runtime remains the distinct `operation_conflict` error. ECC CLI preserves its existing blocking lock behavior so current scripts continue to serialize.

A Layout Edit Session acquires the Workspace Ownership Lock at `layout.edit.begin` and holds it until successful save, explicit discard, Workspace Session close or Runtime process exit. This protects the source revision, native DB and publish targets for the entire editing lifetime. Save advances Workspace Revision and commits Engineering Snapshot before releasing the lock; discarded or process-lost edits publish nothing, and the kernel releases the file lock on process loss.

Workspace-independent Project and Workspace Spec commands use one lazy ECC Runtime process that Electron starts on first use and closes with the application. This is an Electron routing detail using the same ECC executable and private contract, not a separate module, binary or domain concept; Workspace execution and persistent editing never use that process.

`workspace.open` is a Workspace Open Transaction: it briefly acquires the Workspace Ownership Lock, loads the writable canonical Workspace, validates its current Snapshot and supplied machine Bindings, applies only transient bindings, loads the Operation Ledger and recovers unconfirmed Operations as `interrupted`, then creates the Runtime Session and releases the lock. The lock remains held only by active Operation or Layout Edit work. Project lists, Compare and other Pure Workspace Queries do not call this transaction.

Workspace Bindings remain machine-local and revision-neutral. ECC validates and applies PDK/input paths at create, open and execute time and may refresh Derived Backend Configuration files, but it never writes absolute Binding paths into the Workspace Descriptor or Project Manifest and never advances Workspace Revision or creates an Engineering Snapshot solely because a Workspace is rebound on another machine.

Workspace creation and structural replacement use caller-owned staging trees. ECC validates the complete staged Descriptor, Flow, Derived Backend Configuration, declared inputs and initial Snapshot before atomically exchanging the target directory; a failed call removes only its staging tree and restores any renamed-aside previous Workspace. Direct incremental writes into the committed target are not a supported create or structural-update path.

A Flow Step Commit is complete only after ECC has durably written both the Flow Step outcome and its Engineering Snapshot. ECC Runtime publishes `workspace.committed` only after that commit succeeds and includes the committed revision; a Snapshot failure produces `engineering_snapshot_commit_failed`, fails the Operation, preserves the preceding readable Snapshot and emits no commit notification.

Flow state, Engineering Snapshot and commit metadata use an Atomic Engineering Commit. ECC stages and validates the complete replacement before atomically publishing it; if any part fails, it restores the preceding committed set, returns `engineering_snapshot_commit_failed` (or the more specific commit error), and emits no committed-result notification. CLI and Runtime consume this same Engine result and do not implement separate rollback logic.

Runtime Events are transient notifications rather than a durable event stream. They may be duplicated, delayed or lost; Electron deduplicates and detects sequence gaps where possible, then rereads the Execution Snapshot or persisted Engineering Snapshot. No correctness rule, Flow continuation, QoR or Signoff decision depends on event delivery or Renderer acknowledgement.

ECC CLI and ECC Runtime invoke the same headless Engine mutation and execution interfaces. CLI remains a direct Engine caller and never calls ECC Runtime; its command names, selectors, output contract and presentation stay at the CLI edge. Workspace creation, structural and configuration updates, rerun preparation, saved layout edits and Flow execution all use Engine Commit paths that advance Workspace Revision and write Engineering Snapshot before success. CLI `status`, `log`, `report`, `check` and `signoff inspect` remain Pure Workspace Queries and never create or refresh an Engineering Snapshot.

Snapshot-less Workspaces from before this contract are outside the compatibility boundary. Studio reports `ENGINEERING_SNAPSHOT_MISSING`; users recreate the Workspace or use the existing explicit overwrite workflow. ECC and Studio do not infer, convert or silently materialize an Engineering Snapshot for those Workspaces, and this plan adds no migration command.

CLI `--overwrite` keeps its existing temporary renamed-aside backup only for failed replacement recovery and removes it after a successful rebuild; it does not add a Project Workspace or preserve user-visible result history. Studio structural Workspace Update keeps its explicit user choice for a durable Workspace Replacement Backup, so the Runtime never creates an archived Workspace implicitly.

ECC is the only Engineering Snapshot producer and writer. The Snapshot is required as Studio's atomic, revisioned engineering read model; it is not a replacement CLI query API. Electron reads committed Snapshot files directly with path, size, schema, Workspace identity and revision validation so inactive Workspaces and Project Comparison never require a Runtime process; Runtime events are invalidation hints only. CLI inspection keeps its existing direct reads of `flow.json` and declared Step artifacts. `report qor`, `report checklist` and `report summary` retain their current report-specific behavior, including writing the requested or default `signoff/` report file; that output is distinct from Snapshot publication. No CLI query or report command creates or refreshes an Engineering Snapshot. The existing `workspace.engineering_snapshot` RPC remains only during migration and is removed after its consumers use the persisted read path, avoiding two permanent read contracts.

Workspace hydration used by `report qor`, `report checklist`, `report summary` and `signoff inspect` uses ECC's `read_only=True` loader path. It may read the committed Workspace model but must not recover file transactions, migrate legacy configuration filenames, validate-and-rewrite configuration or append Workspace logs. The report destination remains the only intentional write for report commands.

Workspace Revision is one monotonic sequence for every durable Workspace transition. Create starts at revision 1; structural or configuration updates, rerun preparation, saved layout edits and each Flow Step Commit advance it once. An Operation validates its expected starting revision and adopts revisions produced by its own commits while the Workspace configuration remains immutable; competing mutations are rejected while that Operation is active. No separate Configuration Revision or Engineering Revision is introduced.

ECC Runtime persists a bounded Operation Ledger with each Workspace and uses it with live runtime state to answer `workspace.snapshot`. The Ledger always retains the active Operation and the 256 most recently completed terminal Operations, ordered by completion; older records and their Command ID deduplication results are removed after a later Operation becomes terminal. Reopening marks any previously nonterminal outcome that cannot be confirmed as `interrupted`. It is not a user-visible Operation history, and retaining every historical run, pagination and history-specific migrations are outside this contract. Electron does not persist or reconstruct a competing Operation state machine, and the Execution Snapshot never substitutes for Engineering Snapshot facts.

Normal application exit never silently cancels active work. When blockers exist, the user may cancel shutdown or enter safe draining; Force Quit becomes available immediately after draining starts, without a timed delay. An explicit Force Quit attempts cancellable Operations and state flush for up to three seconds, terminates remaining Runtime processes, and relies on the Operation Ledger to recover unconfirmed work as `interrupted` on the next open.

Normal Operation cancellation is cooperative at Flow Step boundaries. A queued Operation may cancel immediately; while an EDA tool is running, Runtime persists `cancelRequested=true` and reports Cancelling without signalling the tool. After that Step reaches its terminal Flow Step Commit, Engine checks cancellation before starting another Step and Runtime records `cancelled`. Force Quit is the only path that terminates a running process; an outcome it cannot confirm is later recovered as `interrupted`, never `cancelled` or succeeded.

The Studio backend runtime remains part of ECC and is distributed with ECC rather than as an ECOS Studio-owned Python module or binary. ECOS Studio invokes this private ECC Runtime to manage Workspace Runtime Sessions and the complete Operation lifecycle, including protocol validation, events, cancellation, interruption recovery, persistent DB coordination and layout or floorplan editing. Each Workspace with active runtime work receives a dedicated Workspace Runtime Process so different Workspaces retain independent execution, native state and failure domains; Electron releases that process after its Operation, editing and finalization work is complete. ECC's headless engineering modules remain the sole authority for Workspace configuration, execution, Engineering Snapshots, QoR, Signoff and Artifacts. Electron continues to own product policy, path authorization, subprocess supervision and presentation queries; it does not reimplement the Runtime state machine. The runtime contract is maintained for the ECC version pinned by Studio and is not a public third-party compatibility promise. This supersedes ADR-0027 because avoiding a separately owned and packaged Studio runtime is preferred over independent Adapter ownership.

## Required protocol follow-up

The ownership migration is deliberately wire-compatible: its first phase preserves existing JSON-RPC method names, request and response fields, error codes and Runtime Events while changing only implementation ownership, packaging and the Electron launch command. After parity and packaged smoke checks pass, a required second phase cleans the private protocol atomically across ECC and Studio: remove the transitional `workspace.engineering_snapshot` read, remove Adapter-specific names and capabilities, narrow mixed responses to their canonical domain models, bump the private protocol version, and delete superseded compatibility code. The migration is not complete while both Snapshot read paths or Adapter terminology remain supported indefinitely.

### Phase-two cleanup checklist

- Delete the transitional `workspace.engineering_snapshot` RPC after all Electron Snapshot consumers read the persisted file directly.
- Delete `adapterVersion`, `runtime.adapter.v1`, Adapter-named capability checks, compatibility DTOs and old error/field aliases from ECC, shared contracts, Electron and tests.
- Rename remaining internal references from Adapter terminology to ECC Runtime and remove the old `ecos-ecc-runtime-adapter` packaging, wrapper and resource assertions.
- Keep exactly one canonical Snapshot read path, one canonical Runtime capability vocabulary and one private protocol version; fail CI if deprecated names or duplicate paths return.
- Release the ECC and Studio changes as one pinned compatibility update, then remove migration-only branches rather than preserving them indefinitely.

## Cross-repository rollout

The rollout is ordered so every published Studio revision has a runnable backend: first merge and package the compatible ECC Runtime and Engine Commit changes; then update ECOS Studio's ECC gitlink and switch Electron from the adapter binary to `ecc rpc serve`; only after ECC/Studio parity and packaged smoke checks pass, perform the required protocol cleanup. Deleting the Studio adapter before the ECC replacement is available is not a valid intermediate state.

## Merge gates

The ownership change is not mergeable on unit tests alone. ECC must pass Ruff, the full Python suite, PyInstaller and a framed-stdio smoke covering handshake, create/open, Execution Snapshot, Flow Operation, cancellation and interrupted recovery. Studio must pass frozen-install, typecheck, lint/format, Electron/Renderer tests, build and desktop smoke. The parent packaging build must pass for resource or launch changes. Cross-component checks must cover one ECC-generated Workspace opened by Studio, one Studio-generated Workspace continued by CLI, `--overwrite` rollback, Snapshot missing/invalid and revision conflict, Workspace Busy lock behavior, background execution, Force Quit recovery and Layout/Floorplan edit lock lifetime. Packaged resources must contain one `ecc` executable and no adapter binary.

The implementation moves the current `ecos/runtime-adapter/ecos_runtime_adapter` modules directly into ECC's `chipcompiler/runtime` namespace, preserving the established file split and behavior while rewriting imports. Its tests move to ECC's `test/runtime`; `ecos/runtime-adapter`, its requirements file, wrapper, duplicate package and duplicate tests are deleted. No forwarding package, symlink or parallel implementation is retained.

The Runtime's existing `jsonrpcserver>=5.0.9,<6` dependency becomes a direct ECC project dependency and is collected by the single ECC package. The Adapter requirements file is deleted; no second environment installs the transport dependency.

All CLI Workspace configuration writes use the ECC Engine transaction and commit paths, including `ecc param set/unset --workspace`, `ecc workspace refresh`, Project-managed create/update and `ecc run --overwrite`. CLI retains its command-line precedence, output records, blocking lock acquisition and temporary overwrite backup, but its private parameter rollback/Snapshot path is removed. In phase one, read-only CLI commands (`status`, `report` and `signoff inspect`) keep their existing pure-query implementations and output contracts; they do not become Snapshot writers or require a read-model migration. Any later unification around persisted Snapshot reads is a separate change.

CLI keeps parsing product selectors (`--resume`, `--from`, `--to`, `--only`, `--force` and preset selection) and resolves them to canonical ordered `step_ids`. It passes those IDs in an `ExecutionPlan` to ECC Engine; Engine owns dependency validation, selected-step execution, Atomic Engineering Commit and revision advancement without learning CLI flag names.

ECC `ExecutionResult` exposes `succeeded`, final state, optional single-step identity, ordered `executed_steps` and optional `failed_step`. CLI maps this headless result to its existing `StepRunResult`/`CommandResult` records; Engine never imports CLI result types, and no CLI rescan of `flow.json` is required to infer partial execution.

When the requested CLI target is already complete and no explicit rerun selector is supplied, Engine returns a successful no-op without starting an Operation, writing Workspace files, advancing Revision or refreshing Engineering Snapshot. Explicit `--only --force`, `--from` or equivalent rerun intent remains a mutation and receives normal commit semantics.

Agent, Quick Start and background product actions continue through Electron Product Commands. They never import ECC or call Runtime methods directly; Electron performs authorization, confirmation, Workspace ownership and revision checks before the ECC Runtime invokes the shared Engine contract.

Known Engine failures remain Stable Domain Errors across CLI, direct Engine and Runtime transport. Runtime maps their code, message and structured details into JSON-RPC without leaking Python traceback or internal diagnostics; only genuinely unclassified exceptions degrade to `command_failed`.

Phase one preserves the on-disk Workspace formats and filenames: `home/params.toml`, `home/flow.json`, `home/engineering-snapshot.json` (schema v2), `home/engineering-snapshot.stale.json`, `home/workspace-commands.json` and `home/runtime-commands.json`. Runtime ownership migration is not a disk-format migration; any future schema change is a separate versioned decision.

Protocol v2 requires `rpc.hello` before any other command on the control process and every Workspace Runtime Process. Electron sends `protocolVersion: 2`; ECC returns protocol version, ECC package version and explicit capabilities for Workspace Spec, Execution Snapshot, persisted Engineering Snapshot, persistent DB and layout editing. A version mismatch or missing required capability fails as `runtime_incompatible` before any Project or Workspace write. Adapter-specific `adapterVersion` and `runtime.adapter.v1` names are removed rather than aliased.
