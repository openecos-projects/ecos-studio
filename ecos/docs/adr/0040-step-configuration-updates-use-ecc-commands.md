# Step Configuration uses the ECC Parameter Catalog and domain commands

ECOS Studio and the Agent submit a Flow Step identity, canonical parameter patch, Workspace Handle, expected Workspace Revision and command identity through `workspace.updateStepConfiguration`. ECC resolves and validates the parameters, maps them to tool configuration targets, commits the complete patch atomically and advances the Workspace Revision once; file names, `config/*.json` paths, JSON paths and the legacy `workspace.syncConfig(configPath)` protocol are not part of the cross-process contract.

ECC accepts only parameters applicable to the identified Flow context. For one atomic patch, ECC resolves each changed parameter's catalog `applies` value against the current Flow and invalidates from the earliest affected Step. Parameters first applied at CTS therefore preserve Synthesis, regardless of whether their internal target is a backend semantic value or a tool configuration field. Design inputs, PDK family, Flow structure and PDK Resource Overrides remain structural Workspace updates outside this rule.

One ECC-owned Parameter Catalog defines every user-configurable Workspace Parameter and Step Option for both ECC CLI and ECOS Studio. Membership in the catalog means the parameter is configurable, so the schema does not carry a redundant per-field editable flag. The products may expose different subsets and presentations, while Studio's specialized editors own layout only.

Studio requests an editor model containing catalog metadata and the current Workspace-resolved value for each applicable parameter. It does not read `config/*.json`, infer controls from JSON values or maintain JSON-path mappings. Generated and protected tool fields remain ECC implementation details and are excluded from the editor model; any future diagnostic view of those fields is a separate read-only capability.

The existing Step Configuration read command returns ordered parameter records containing only canonical `param`, `type`, current `value`, `default`, `applies`, `description` and optional `range`, `choices` or `unit`, together with Step and Workspace identity. It does not return `maps_to`, `config_target`, `json_path`, `pdk_target` or filesystem paths. A Step with no applicable catalog entries returns unavailable so Studio can hide the action; an invalid or incomplete Descriptor fails instead of returning a missing configuration or synthesizing defaults. The update command accepts the same Step identity plus a map from canonical parameter names to replacement values under `parameters`, replacing the raw nested `options` payload.

Each parameter has one editing location in Studio: the Flow Step identified by its normalized catalog `applies` value. A shared backing configuration does not expose the same parameter on later Step pages. If the catalog contains no entries for a Step, Studio hides its Step Configuration action. Consequently DreamPlace parameters belong to Placement, while Legalization, Timing Optimization and DRC expose no Step Configuration until ECC adds catalog entries for them; CLI step filtering follows the same rule.

A catalog entry declared as `type="json"` remains one Structured Parameter Value. Studio may reuse its existing object and table editor for that one value and submits the complete value under its canonical parameter name. Nested members do not become additional schema entries, and this support does not expose or recreate a raw tool-configuration editor. ECC retains the upstream top-level object-or-array validation without adding a nested JSON Schema.

The catalog uses the upstream CLI's dotted parameter identifiers, such as `design.frequency_mhz` and `cts.max_fanout`, as the only public names across TOML, CLI and Studio contracts. TOML represents their prefixes as tables. Backend keys such as `frequency_max` and tool JSON paths remain private catalog targets; they are not accepted as alternate public names and do not create a legacy alias or automatic migration path.

Every catalog value with a backend semantic target or tool configuration target is persisted under the Workspace Descriptor's `[params.*]` tables. Workspace Parameters and Step Options do not have separate storage sections; these terms describe consumer breadth rather than storage or command routing. The existing catalog `applies` value identifies the earliest affected Flow Step, including when one patch changes multiple parameters. ECC does not add a second invalidation-scope field or ask Studio to split the save into multiple commands or Revisions.

Catalog entries with a `pdk_target`, such as `pdk.tech` and `pdk.libs`, are PDK Resource Overrides rather than Workspace Parameters or Step Options. They retain the upstream Project Configuration behavior under `[pdk.overrides]`. A Workspace Descriptor records only portable PDK requirements and provenance under `[pdk]`, while machine-resolved resource paths remain in the transient Workspace Binding; Studio excludes these entries from Step Configuration.

`chipcompiler.data.parameter_schema` is the shared catalog interface for ECC Engine and CLI callers. The upstream tool-specific schema definitions move from `chipcompiler.cli.project.config_params` to `chipcompiler.data.config_params`, while `chipcompiler.cli.project.params` remains a compatibility re-export to avoid broad CLI churn. The existing runtime parameter container in `chipcompiler.data.parameter` retains its separate responsibility and is not another catalog. No additional catalog class, adapter or facade is introduced.
